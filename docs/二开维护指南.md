# 二开维护指南

## 当前基线

- 上游版本：`spv8.4`（提交 `e4332c1`）
- hajimi 合并分支：`upgrade/spv8.4-maintenance`
- 油猴元数据版本：`8.4.0`
- 技术栈：TypeScript、Vue 3、Pinia、Rollup、Vitest、sql.js
- 代码规模：约 415 个源码文件、12 万行源码

上游 8.4 并不位于上游 `main`，而位于 release 分支/tag。后续同步上游时应以明确 tag 为基准，不要假设 `upstream/main` 是最新发布版。

## 先理解三条主链路

### 1. 启动链路

```text
src/index.ts 或 src/entry-extension.ts
  → presentation/bootstrap/init.ts
  → presentation/bootstrap/api-registry.ts
  → presentation/bootstrap/startup.ts
  → presentation-v2/bootstrap/index.ts
```

旧 UI 与新 UI 会共同启动。实例互斥、宿主 API 探测、菜单注册问题应从这条链路查，不要从具体页面反向猜测。

### 2. 表格更新链路

```text
UI / AutoCardUpdaterAPI
  → service/table/update-orchestrator.ts
  → AI / prompt / table edit parser
  → storage-frame-v2-persist.ts
  → JSON 或 SQLite 存储
  → replay / history / UI refresh
```

这是风险最高的核心链路。一次更新可能同时影响表格数据、帧、历史记录、回放基线和可视化器状态。修改前先搜索对应测试，不要只验证最终 UI。

### 3. 新 UI 链路

```text
Vue page/surface
  → composable
  → Pinia store 或 AutoCardUpdaterAPI
  → service
```

页面组件应该负责布局与组合；可复用交互放 composable；跨页面状态放 store；业务规则和持久化放 service/data。

## 已知基线测试问题

合并后的类型检查和正式构建通过，架构守卫为 0 违规。上游 8.4 基线目前至少有 9 个失败用例：

1. 多 isolationKey 边界 checkpoint 写入中途失败后，内存回滚会留下 `checkpoint: undefined`，没有恢复到逐字段完全一致。
2. 手动重填单表基底替换已经改用 `perSheetCheckpoints`，但同一测试仍断言旧增量 `logEntries` 保留一条，测试期望与当前清理实现不一致。
3. `tests/presentation/bootstrap/api-groups/worldbook-ai-api.test.ts` 的 7 个旧用例仍假设浏览器端可直接调用自定义 API/酒馆连接管理器；8.4 已把 `callAI` 收敛为受限代理，因此这些 spy 不再被调用，测试契约尚未跟进新的安全边界。

这些失败不是本次文档整理引入；`spv8.4` tag 中源码与测试即为这组组合。第一项应按真实回滚缺陷修复，第二项要先确认产品语义再决定修实现还是修断言，第三项应围绕“受限代理”重写 API 合约测试，不能为了绿测恢复已经封禁的公开密钥调用路径。

完整 Vitest 套件还存在执行结束慢、worker 长时间不退出的问题，建议后续按 service、presentation、presentation-v2 分组配置独立测试任务，并为 CI 增加超时与句柄诊断。

## 当前主要维护债务

### P0：高风险巨型编排文件

| 文件 | 约行数 | 问题 | 建议拆法 |
| --- | ---: | --- | --- |
| `service/table/update-orchestrator.ts` | 2777 | 更新状态、AI 调用、批次、持久化揉在一起 | 拆为 session、batch planner、AI executor、commit coordinator |
| `service/table/storage-frame-v2-persist.ts` | 2046 | 校验、帧生成、SQLite/JSON 写入耦合 | 拆 validator、frame builder、backend adapter、transaction |
| `service/chat/chat-service.ts` | 1914 | 消息读取、裁剪、格式化、宿主兼容混合 | 拆 reader、normalizer、range selector、host adapter |
| `presentation-v2/surfaces/visualizer/VisualizerSurface.vue` | 2149 | 页面、状态、保存和面板逻辑过载 | 保留 shell，面板下沉组件，行为下沉 composable |

这些文件不应整文件重写。每次只提取一个可独立测试的职责，并保持公开函数签名不变。

### P1：双 UI 与适配重复

`presentation/` 和 `presentation-v2/` 同时存在是兼容需求，但容易出现同一规则实现两遍。处理方式：

1. 把规则归并到 service。
2. `api-groups` 只暴露稳定 DTO 和调用。
3. 旧 UI 与 Vue UI 各自只保留展示适配。
4. 新需求默认只给 Vue UI 增加界面；若必须兼容旧 UI，再增加薄适配。

### P1：全局 API 缺少强类型边界

`AutoCardUpdaterAPI` 通过 `Object.assign` 和 `any` 组装，调用方很难知道稳定契约。建议新增单一 `AutoCardUpdaterApi` interface，并让各 `create*Api` 返回明确分组类型。完成类型收口前，不要随意重命名对外方法。

### P2：构建版本来源不统一

包版本、油猴 `@version`、git tag 和内部 build version 目前不是同一个来源。后续可增加发布脚本，从环境变量或 tag 注入版本，避免再次出现 tag 已到 8.4、banner 仍为旧版本的情况。

## 推荐的二开工作流

1. 从最新维护分支创建功能分支。
2. 运行 `corepack pnpm analyze`，记录目标文件当前规模。
3. 找到 service 层入口和现有测试；没有测试时先补最小行为测试。
4. 修改源码，不直接碰生成产物。
5. 运行 `typecheck`、相关测试和完整测试。
6. 运行 `build`，让 bundle、根 `index.js` 和 JSON 包装文件同步更新。
7. 检查 `git diff --stat`，确认没有意外导入用户数据、缓存或临时文件。

## 上游同步流程

```bash
git fetch upstream --prune --tags
git switch -c upgrade/spvX.Y-maintenance main
git merge --no-ff spvX.Y
```

冲突处理优先级：

1. `src/` 源码：按行为逐项合并。
2. 测试：保留两侧覆盖并修正断言。
3. 文档/版本：以新发布基线为准，保留二开说明。
4. `dist/`、`index.js`、酒馆 JSON：源码解决后重新构建生成，不手工拼接。

## 第一阶段重构建议

建议后续按以下顺序实施，每一步都可独立提交和回滚：

1. 为 `AutoCardUpdaterAPI` 建立类型契约，不改变运行时行为。
2. 从 `update-orchestrator.ts` 提取无副作用的批次规划与输入校验。
3. 给 storage frame V2 建立统一 backend interface，隔离 JSON/SQLite 分支。
4. 把 `VisualizerSurface.vue` 的保存、导航和面板状态逐个迁入 composable。
5. 对 `chat-service.ts` 建立 host gateway，减少对 SillyTavern 全局对象的直接依赖。

不建议一开始就切换严格 TypeScript、删除旧 UI 或替换整个存储层；这三类改动影响面过大，应等核心链路测试覆盖提升后再做。
